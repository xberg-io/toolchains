# toolchains

The xberg-io toolchain baseline for [mise](https://mise.jdx.dev): one set of tool and language versions that
every repository installs locally and in CI.

## Contents

| Path | Purpose |
|---|---|
| `baseline.toml` | Canonical versions, in mise `[tools]` syntax. Renovate bumps them here first. |
| `scripts/toolchains.py` | `check` reports drift from the baseline and the task sets; `sync` rewrites a repository's pins and shared tasks. Standard library only, Python 3.11+. |
| `task-sets/` | Named sets of mise tasks that `sync` writes into a repository (see [Task sets](#task-sets)). |
| `default.json` | Renovate preset for consumers: turns off upstream bumps for baseline tools, groups repo-owned ones. |

## Consuming repositories

A repository commits:

- `mise.toml` with the tools it needs, using the baseline's exact key, version and table options (`node = "26.12.1"`,
  `"github:Goldziher/poly" = "0.29.0"`). An alias of a baseline tool (`nodejs`, `core:node`, `aqua:…`) is drift;
- `mise.lock`, generated by `mise lock`, covering `linux-x64`, `linux-arm64`, `macos-arm64` and `windows-x64`;
- `rust-toolchain.toml` for Rust, which stays authoritative for components and targets. Declaring `rust` in
  `mise.toml` is an error; the file's `channel` is checked against the baseline's `rust`;
- `toolchains.toml` recording the baseline tag it follows, and any override:

```toml
baseline = "v1.0.0"

[overrides.node]
version = "22.20.0"
reason = "engines floor smoke test runs on the oldest supported Node"

[overrides."github:Goldziher/poly"]
version = "0.28.4"
reason = "example: hold the previous release until a regression fix ships"
```

Only `mise.toml` is read; profile files such as `mise.ci.toml` are not checked.

Tools the baseline does not list (for example `wasm-bindgen-cli`, which must match `Cargo.lock`) are owned by the
repository. Renovate updates them when the repository extends `github>xberg-io/toolchains`.

ai-rulez is not pinned anywhere: tasks run `npx -y ai-rulez@latest`, which needs the baseline's `node`.
`governance:hooks:install` allows the poly hooks' `npm` channel first, so they run `npx -y ai-rulez@latest` too, and
falls back to an `ai-rulez` on PATH.

## Moving to a new baseline

```sh
git clone --depth 1 --branch v1.1.0 https://github.com/xberg-io/toolchains /tmp/toolchains
python3 /tmp/toolchains/scripts/toolchains.py sync --baseline /tmp/toolchains/baseline.toml --ref v1.1.0
mise lock
python3 /tmp/toolchains/scripts/toolchains.py check --baseline /tmp/toolchains/baseline.toml
```

`sync` also moves the version files mise does not read (see the table below), so a baseline bump is one
`sync`; it prints Dockerfile tags that still disagree, since it does not rewrite them.

`mise lock` after `sync` is required, not optional: shared tasks can pin their own tools (`governance:check` and the
`plugin` tasks run on a task-level `node = "26.13.0"`), and a lock without that version fails `--locked` CI with
"No lockfile URL found for node@26.13.0". With `MISE_TASK_RUN_AUTO_INSTALL=false` and a stale lock, the task falls
back to whatever `node` is on PATH without a warning. `check` exits 1 when a committed `mise.lock` lacks a version a
selected task pins.

`check` exits 1 on drift and 2 when nothing could be checked: a missing `mise.toml`, or neither a declared tool nor
a version file covered by the baseline. It lists the repository-owned tools it skipped. A pin of ai-rulez under any backend
(`github:Goldziher/ai-rulez`, `npm:ai-rulez`) is drift: use `npx -y ai-rulez@latest` instead. It also exits 1 when
the repository root still holds go-task files, since the org runs its tasks with mise: a `Taskfile.yml`,
`Taskfile.yaml`, `Taskfile.dist.yml` or `Taskfile.dist.yaml` in any letter case, or a `.task/` directory. In a git
checkout only tracked files count, so an ignored `.task/` cache passes; elsewhere the files on disk are checked.

Version files mise does not read must agree with the baseline as well, or with the tool's override in
`toolchains.toml`. In a git checkout the tracked files count, outside `node_modules`, `vendor`, `vendored`,
`third_party` and `third-party` directories; a checkout git cannot read (for example one it reports as dubious
ownership) is an error, exit 2, never a walk of the disk. A directory without `.git`, such as a `git archive`
export, is walked on disk, skipping those directories and `.venv`, `target`, `dist` and `build` too. `check` lists
the files it compared and the ones it could not, and exits 1 when one disagrees:

| File | Compared with | Match | `sync` |
|---|---|---|---|
| `.nvmrc`, `.node-version` | `node` | exact; a leading `v` is ignored, a bare major (`26`) or `lts/*` is drift | rewrites, keeping a `v` |
| `.python-version` | `python` | exact, first version line | rewrites the first line |
| `.ruby-version` | `ruby` | exact; a `ruby-` prefix is ignored | rewrites, keeping `ruby-` |
| `.tool-versions` | each baseline tool it names (`nodejs`, `golang` included) | exact, first version; `system`, `lts` and `latest` are skipped, `java` only when `temurin-<x.y.z>+<build>` | no |
| `package.json` `packageManager` | `pnpm` | exact; a `+sha512.…` suffix is ignored, other package managers are skipped | rewrites, dropping the hash, which names the old release |
| nested `rust-toolchain.toml`, any `rust-toolchain` | `rust` | exact, like the root file: `1.99` is drift against `1.99.1`; named channels (`nightly`, `nightly-2026-01-01`, `stable`, `beta`) are listed as not checked; invalid TOML is drift | rewrites numeric channels |
| `Dockerfile`, `Dockerfile.<name>`, `*.Dockerfile`, `Containerfile` | `node`, `python`, `go`, `ruby` | major.minor of official `node`, `python`, `golang`, `ruby` images | no, prints the drift |

Exact matching keeps every place that installs a runtime on the version CI locks. That includes
`.python-version`: `3.13` is drift against `3.13.18` on purpose, since pyenv and uv resolve it to whatever patch
is installed. The root `rust-toolchain.toml` is checked with the mise pins and must name the baseline channel
exactly; a repository that needs another toolchain for fuzzing or Miri keeps it in a nested file.

Dockerfile tags are compared on major.minor only, because the official images publish patch tags after the release
the baseline already follows: `FROM node:26.13-slim` and `FROM node:26.13.1` pass against `26.13.0`; `FROM node:26`,
`node:latest` and an untagged `node` are drift. `Dockerfile.<name>` with a template or document extension (`.j2`,
`.jinja`, `.tmpl`, `.tpl`, `.template`, `.md`, `.txt`) is not a Dockerfile. An `ARG` default in the same file
resolves a `${VAR}` tag, and `${VAR:-x}` or `${VAR-x}` falls back to `x`; a tag that still names an argument
without a value is listed as not checked. Other registries (`ghcr.io/…/node`) and other images are not compared.

`sync` writes nothing when any pin cannot be rewritten (for example a `[tools.node]` subtable) or when table options
differ from the baseline; fix those by hand.

## Task sets

Tasks that several repositories define with the same body live here as named sets, so a fix lands once and
repositories pick it up on the next baseline move. A repository opts in from `toolchains.toml`:

```toml
baseline = "v1.6.0"
task_sets = ["governance", "governance-check", "lint-format"]

[task_overrides]
lint = "runs tflint over terraform/, not poly"
```

`sync` (same command as in [Moving to a new baseline](#moving-to-a-new-baseline)) then writes, all generated and
committed:

- `mise-tasks/shared.toml`: the selected sets' tasks, under a header naming the toolchains tag;
- `mise-tasks/.shared/<set>/…`: the sets' file tasks, executable, plus `.manifest`, the list of files sync owns.
  The directory is hidden because mise registers every executable under an included directory as a task;
- `"mise-tasks"` and `"mise-tasks/shared.toml"` in `mise.toml`'s `[task_config] includes`, adding the table when it
  is missing. `includes` replaces mise's default scan, so sync also keeps any default task directory
  (`.mise-tasks`, `.mise/tasks`, …) the repository has.

Dropping a set deletes the files sync wrote for it, as listed in the manifest; dropping the last one also takes
`"mise-tasks/shared.toml"` out of `includes`. Sync writes and deletes only regular files under those two paths, never
through a symlink, and stops without writing when the manifest names anything else or a shipped path already holds a
file sync did not write. Do not edit the generated files: change the set here and tag a release.

A task listed under `task_overrides` is left out of `shared.toml` (with its aliases) and stays the repository's own,
for a body that must differ. Every other task a selected set provides must not be defined locally: `check` exits 1
when `mise.toml` `[tasks]`, a TOML file mise loads (an `includes` file, or any `*.toml` under an included directory),
or an executable file task defines one of those names or aliases. It also exits 1 on an unknown set; an override
without a reason, for a task no selected set provides, or for a task the repository does not define; a missing
include; and any generated file that differs from what `sync` would write, including its exec bit. In a repository
that selects a set or has a manifest, every file under `mise-tasks/.shared/` must be one sync wrote.

Repository specifics come from the environment with a default, never a repository name: set `DOCS_DIR` (default
`docs-site`), `BATS_LIB_REF` or the `deps-refresh` variables in `mise.toml`'s `[env]`.

### Why these members

A task joins a set when its body is identical in at least two repositories and in at least half of the repositories
that define the name, so overrides stay the exception. A set also gives no repository a task it does not define: a
member only some of a set's repositories define moves to a set of its own, or stays local when that set would ship
no file task and replace fewer than six local definitions. Counts are repositories with that exact body /
repositories defining the name, from every repository's default branch on 2026-10-29, after each repository removed
the tasks it does not use (remote file tasks count by source file).

## Lock gaps

CI locks the whole baseline for all four platforms. These cannot be locked and are allowed by name: `dotnet` and
`rust` (installed by script, no checksummed artifact), `aws-cli`, `bats` and `ruby` on Windows, `cargo-sort` on
linux-arm64. Jobs on those platforms keep their existing setup action for that tool.

## Changing the baseline

Edit `baseline.toml`, keep `default.json`'s disabled list equal to its keys (a test enforces this), and tag a
release. Patch versions follow the newest patch of the line in use; moving a minor or major line is a reviewed
change.
